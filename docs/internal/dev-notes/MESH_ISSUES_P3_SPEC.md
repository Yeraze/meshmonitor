## 0. Scope and mesh-impact statement

Phase 3 adds **no new mesh traffic of any kind**. Everything here is either a
read of rows already on disk, a settings write, a UI change, or documentation.
The analysis service still sends zero packets and emits zero `dataEventEmitter`
events. The mesh-impact checklist is satisfied by construction, exactly as in
Phases 1 and 2:

1. **Airtime cost:** zero. No packet is generated by any code path in this phase.
   The new Tier C rules read `nodes` columns and `telemetry` rows that other
   services already wrote.
2. **Spam:** none, direct or indirect. Findings still do not touch
   `dataEventEmitter`, so they cannot fan out to the automation engine, Apprise,
   desktop notifications, or MQTT publish. Notifications for mesh issues remain
   **explicitly out of scope** (P1 §5.11); see §8.3 for the follow-up.
3. **Safety timer:** the scheduler's last-run timestamp already lives in
   settings (`mesh_issues_last_run`), so a settings save cannot re-arm it. Phase
   3 adds a settings **section** for this feature, which makes that property
   load-bearing for the first time: WP5 must not add any "save then run" path,
   and the acceptance criteria include restarting the dev container and
   confirming `lastRunTime` survives.

New user-tunable knobs are clamped **server-side at read time** (§2.2), the same
doctrine `clampLookbackHours` already follows, so a bad value in the database
degrades to a bounded run rather than an unbounded one.

**Phase 3 delivers:** the C3 coverage preface, dismiss/undismiss, Tier C
(C1 + C2), a threshold settings UI, the full UI polish backlog from both phase
logs, a user docs page, and a decision on D12 (implemented, not accepted).

### 2.4 Last-run summary persistence

`meshIssuesScheduler.lastRunResult` is an in-memory field, so after a container
restart `/status` reports `lastRunResult: null` and the coverage preface would be
blank for up to a full frequency period (24 h by default). That makes the
headline Phase 3 feature invisible after every deploy, which is not acceptable.

**Decision (P3-D1):** persist a compact summary. In
`MeshIssuesScheduler.execute()`, on **success only** (a failed run must not
overwrite the last good summary), write:

```ts
await databaseService.settings.setSetting(
  'mesh_issues_last_run_summary',
  JSON.stringify({ at: this.lastRunTime, result }),
);
```

`getStatus()` returns the in-memory `lastRunResult` when present; otherwise it
parses the settings key inside a `try/catch` and validates that the parsed value
is a non-array object with a numeric `durationMs`, falling back to `null`
otherwise. The key is user-POSTable (it is in `VALID_SETTINGS_KEYS` so the
allowlist round-trip test passes), so **defensive parsing is mandatory**, not
optional. Size is ~1.5 KB of JSON; the settings value column is TEXT on all
three backends.

`MeshIssuesStatus` gains:

```ts
  /** Resolved + clamped thresholds actually in force for the next run. */
  thresholds: ResolvedMeshIssueThresholds;
  /** True when lastRunResult was recovered from settings rather than memory. */
  lastRunResultFromStorage: boolean;
```

### 2.5 C2 feasibility, and what is weakened

The epic asks for "deduped position/telemetry **median** inter-arrival < 5 min".
Investigation of what we actually have:

- **Telemetry cadence: fully available, no new query.** The service already pulls
  `airUtilTx`, `channelUtilization`, `batteryLevel`, `uptimeSeconds` over the
  whole lookback window and `buildTelemetrySeries` already dedupes by
  `(nodeNum, type, timestamp)`. One device-metrics packet writes several rows
  sharing one timestamp, so the **union of distinct timestamps across the four
  series** is a faithful count of device-telemetry broadcasts. A true median
  inter-arrival is computable in memory, for free.
- **Position cadence: not available in memory.** Positions live in `telemetry`
  under types `latitude`/`longitude`, and the only accessor the service uses is
  `getPositionTelemetryByNode(nodeId, limit, ...)`, one call per node. Running
  that for every node (not just the small infra set A4 uses) is an O(n) query
  fan-out per run and is rejected on cost. Pulling every `latitude` row for the
  lookback window through `getTelemetryByTypesSince` is also rejected: on a
  200-node mesh with 7 days of positions that is a six-figure row count loaded
  into memory for one rule.

**Resolution (P3-D2), two-stage, bounded:**

*Stage 1 (one query, whole mesh).* A new portable aggregate:

```ts
// src/db/repositories/telemetry.ts
export interface TelemetryCadenceAggregate {
  nodeNum: number;
  telemetryType: string;
  /** COUNT(DISTINCT timestamp) — the dedup the epic mandates, done in SQL. */
  sampleCount: number;
  firstTimestamp: number;
  lastTimestamp: number;
}

async getTelemetryCadenceAggregates(opts: {
  telemetryTypes: string[];
  sinceMs: number;
  sourceIds: string[];
}): Promise<TelemetryCadenceAggregate[]>
```

Drizzle query builders only: `select({ nodeNum, telemetryType, sampleCount:
sql<number>\`COUNT(DISTINCT ${telemetry.timestamp})\`, firstTimestamp:
min(...), lastTimestamp: max(...) }).groupBy(nodeNum, telemetryType)`.
`COUNT(DISTINCT col)`, `MIN`, `MAX` and `GROUP BY` are identical on SQLite,
PostgreSQL and MySQL. Coerce `nodeNum` with `Number()` (BIGINT on PG/MySQL).

Stage 1 gives a **mean** inter-arrival:
`(lastTimestamp - firstTimestamp) / (sampleCount - 1)`.

*Stage 2 (candidates only).* Nodes whose stage-1 mean is below
`overBroadcastSeconds * OVER_BROADCAST_CANDIDATE_FACTOR` are candidates. For
those only, fetch the actual timestamps and compute the exact median:

```ts
async getTelemetryTimestamps(opts: {
  nodeNums: number[];
  telemetryTypes: string[];
  sinceMs: number;
  sourceIds: string[];
}): Promise<Array<{ nodeNum: number; telemetryType: string; timestamp: number }>>
```

Called in chunks of 25 node numbers (`inArray`), mirroring
`buildPositionSpans`'s `POSITION_SPAN_CHUNK_SIZE` loop. The candidate set is
small by construction: it contains only nodes already broadcasting faster than
twice the threshold.

**Why the mean gate is safe:** a node that is offline for part of the window has
its mean inflated by the gap, so the gate **under**-selects. Under-flagging is
the direction every other guard in this epic chooses deliberately (D3, D9).
Recorded and stated in the docs page.

**Not weakened:** the final determination is a true median, as the epic asks.
**Weakened:** the candidate *gate* is a mean, so a node with an extreme
duty-cycle pattern (a burst then a multi-day silence) can be missed. Documented
in §8.1.

Types used for C2: `['latitude']` for position (one row per position report;
using both axes would double the count), and the in-memory device-telemetry
series union for telemetry. Positions therefore cost exactly one stage-1 query
plus at most `ceil(candidates/25)` stage-2 queries per run.

### 3.3 C1, existing flags folded in

Three separate issue types, all node-attributed, all `nodeSubjectKey(nodeNum)`,
so a node can carry one of each without subject-key collisions.

**`C1_excessive_packets`** fires when `node.isExcessivePackets === true`.
severity `warning`, confidence `medium` (the flag is our own detector, and the
pooled rate is a max over vantages, not a measured mesh-wide total).
Evidence: `packetRatePerHour`, `role`, `roleName`, `sources`.
Recommendation: *"This node is putting a lot of packets on the channel. Check
its position and telemetry broadcast intervals, and any auto-responder or
integration attached to it."*

**`C1_key_security`** fires when any of `keyIsLowEntropy`,
`duplicateKeyDetected`, `keyMismatchDetected` is true. **One finding per node**
(not three), carrying `clauses: string[]` naming which fired.
severity `warning`. confidence `high` when `keyIsLowEntropy` is among the
clauses (a deterministic property of the key itself), otherwise `medium`
(a duplicate or mismatched key has benign causes, notably a re-flashed node).
Evidence: `clauses`, `details` (from `keySecurityIssueDetails`), `sources`.
Recommendation: *"Regenerate this node's key from the device (factory reset of
the key material), then re-exchange NodeInfo on the node's channel."*
The recommendation deliberately says *channel*, not DM: a PKI DM uses the stored
key, which is the thing in question (CLAUDE.md, key repair routing).

**`C1_time_offset`** fires when `node.isTimeOffsetIssue === true`.
severity `info`, confidence `high`.
Evidence: `timeOffsetSeconds`, `sources`.
**No new threshold.** The flag is set by `duplicateKeySchedulerService` against
`TIME_OFFSET_THRESHOLD_MINUTES` (env, default 30). Adding a second threshold
here would let the two disagree. The docs page states where the threshold lives.

**Overlap note (must be in the docs page, §7):** all three C1 conditions are
already surfaced by the Security tab (`securityRoutes.ts`). C1's value is
putting them in one health report next to the routing findings, with the
dismiss/auto-close lifecycle. The docs page says so plainly so a user is not
confused by seeing the same node twice.

### 3.4 C2, over-broadcasting config

Fires when **all** of:
- `node.role != null` and `!OVER_BROADCAST_EXEMPT_ROLES.has(node.role)`
  (a node with an unknown role is skipped, conservatively);
- the deduped median inter-arrival for position **or** telemetry is
  `< ctx.thresholds.overBroadcastSeconds`;
- that stream has at least `OVER_BROADCAST_MIN_SAMPLES` deduped samples
  in-window.

severity `warning` when the node is **not** powered (`!isPowered(batteryLevel)`,
because a battery node over-broadcasting is also burning itself down) or the
median is under half the threshold; otherwise `info`. confidence `medium`.

Evidence: `stream` (`'position' | 'telemetry'`), `medianIntervalSeconds`,
`meanIntervalSeconds`, `sampleCount`, `windowHours`, `thresholdUsed`,
`role`, `roleName`, `sources`. When both streams qualify, emit **one** finding
for the faster stream and carry the other in `otherStreamMedianSeconds`, so a
node never produces two C2 rows under one subject key.

Recommendation: *"This node broadcasts position or telemetry far more often than
the mesh needs. Increase the broadcast interval in its device settings. Roles
that are meant to report often (Tracker, Sensor, TAK Tracker) are exempt from
this check."* No role change is recommended.

```ts
function capList<T>(items: T[]): { items: T[]; truncated: boolean; total: number } {
  const total = items.length;
  if (total <= EVIDENCE_MEMBER_LIST_CAP) return { items, truncated: false, total };
  return { items: items.slice(0, EVIDENCE_MEMBER_LIST_CAP), truncated: true, total };
}
```

Each of the four call sites emits a sibling `<field>Total: n` next to its
existing `<field>Truncated: boolean`:
`membersTotal`, `edgesTotal`, `sharedNeighborsTotal`,
`otherCoveringRoutersTotal`, `clusterMembersTotal`.

### 4.3 D12: evidence redaction (implemented, not accepted)

**Decision (P3-D3): implement it.** P2 §6 D12 deferred name redaction inside
evidence to "Phase 3's dismiss/acknowledge work". It is cheap here because
`buildNodeNameMap(permitted)` already exists in this file and already resolves
names from permitted sources only. Accepting the leak would mean shipping a
route that redacts a node's name in one field (`nodeName`) and discloses it in
another (`evidence.members[].name`) in the same JSON object, which is not a
defensible end state for the phase that is supposed to close the epic.

Add an exported pure helper in the route module (exported for direct unit
tests):

```ts
/** Recursively rewrites evidence so it discloses nothing the caller could not
 *  read directly. Two rules, applied at every depth up to EVIDENCE_MAX_DEPTH:
 *   1. A key named `sources` holding an array of strings is intersected with
 *      `permitted`.
 *   2. An object with a numeric `nodeNum` has its `name` / `longName` / any
 *      `*Name` string that carries a node label REPLACED by
 *      `nodeNames.get(nodeNum) ?? null`. Never merged, always replaced, so an
 *      unpermitted name cannot survive.
 *  Arrays and plain objects are walked; anything else is returned as-is. */
export function redactEvidence(
  evidence: Record<string, unknown>,
  permitted: string[],
  nodeNames: Map<number, string>,
): Record<string, unknown>;
```

A **generic recursive walk** is specified rather than a per-rule field list,
because a per-rule list is exactly the kind of thing that silently rots when a
later phase adds a rule (the Phase 2 evidence-shape lesson). Depth cap
`EVIDENCE_MAX_DEPTH = 6` guards against a pathological shape.

Two named exceptions the walk must handle, and their tests:
- `bestSitedName` (B1) sits next to `bestSitedNodeNum`, not inside an object with
  a `nodeNum` key. Handle it explicitly: when an object has both `<x>NodeNum`
  (number) and `<x>Name` (string), rewrite the name from the map.
- A2b's per-node entries use `longName`, not `name`. Both keys are covered by
  rule 2.

`toWireIssue` calls `redactEvidence(evidence, permitted, nodeNames)` after
parsing and before returning. The finding-level `sourceIds` intersection stays
exactly as it is.

### 4.4 Dismiss / undismiss routes

```
POST   /api/analysis/mesh-issues/:id/dismiss    -> ok(res)   204-style { success: true }
POST   /api/analysis/mesh-issues/:id/restore    -> ok(res)
```

Two POST routes (not one PATCH with a body) to match the `beaconOfferRoutes.ts`
`dismiss` / `restore` precedent in this codebase.

**Permission: `requirePermission('settings', 'write')`** plus a per-caller
visibility check. Justification, in full, because this is a decision a reviewer
will challenge:

- `mesh_issues` is a **global** table with no `sourceId`. Every other
  `requirePermission('nodes', 'write')` call site in the codebase passes
  `{ sourceIdFrom: ... }`, because node writes are per-source. There is no
  source to scope to here, so `nodes:write` would be an unscoped use of a
  resource that is scoped everywhere else, which is worse than no precedent.
- Dismissal is **global state**: it hides the finding for every user, not for
  the caller. That is administrative, and `settings:write` is what already gates
  the other administrative action on this feature (`POST /run-now`, in the same
  router).
- Both are consistent with the "global batch job" family: position estimation's
  `run-now` is also `settings:write`.

**Visibility check (mandatory, defence in depth):** `settings:write` is not the
same grant as source read access, so before mutating, the handler loads the row
(`getMeshIssueByIdAsync`), parses its `sourceIds`, intersects with
`resolvePermittedSourceIds(req, 'nodes')`, and returns
`fail(res, 404, 'MESH_ISSUE_NOT_FOUND', ...)` when the intersection is empty.
A caller must not be able to dismiss (or, by the 200/404 difference, probe the
existence of) a finding it cannot see. Unknown id also returns the same 404.

Both routes `auditLogAsync` (`mesh_issue_dismiss` / `mesh_issue_restore`,
resource `settings`), matching the `run-now` handler's shape, and pass
`req.user!.id` as `dismissedBy`.

Non-numeric `:id` returns `fail(res, 400, 'INVALID_ISSUE_ID', ...)`.

## 10. Spec-level decisions

Each resolves an open question or goes beyond the epic. **Veto candidates are
marked**; the user can overrule any of these before implementation starts.

**P3-D1. The last run's summary is persisted to
`mesh_issues_last_run_summary`.** Without it the coverage preface, the headline
feature of this phase, is blank for up to 24 h after every restart. The
alternative (widen `mesh_issues` or add a table) needs a migration for derived
data that the next run regenerates, which is exactly what P1 §5.12 rejected for
the findings themselves. The cost is one user-POSTable settings key that must be
parsed defensively. **Veto candidate** (the alternative is to accept a blank
preface after restart).

**P3-D2. C2 uses a two-stage mean-gate-then-exact-median for position cadence,
and a pure in-memory median for telemetry cadence.** The epic asks for a median;
a median over every node's positions for a 7-day window is not affordable in one
in-memory pass, and a per-node query is O(n) round trips. Stage 1 is one
portable `GROUP BY` aggregate; stage 2 runs only for nodes already broadcasting
faster than twice the threshold. The gate is a mean, which under-selects on
gappy data, which is the safe direction. See §8.1 for what is lost.

**P3-D3. D12 is implemented, not accepted.** Evidence-level name and source
redaction lands in `toWireIssue` via a generic recursive `redactEvidence`,
reusing the `buildNodeNameMap(permitted)` the route already builds. Accepting
the leak would ship a route that redacts a node name in `nodeName` and discloses
it in `evidence.members[].name` in the same object. A generic walk, not a
per-rule field list, so a future rule's evidence is covered by default. **Veto
candidate** only in the sense that the user could still prefer "document and
accept"; the recommendation is firmly to implement.

**P3-D4. The threshold UI is a standalone `MeshIssuesSection`, not a
`SettingsDraft` extension.** `PositionEstimationSection.tsx` is the exact
precedent: a global batch job, rendered inside `SettingsTab`, owning its own
state and its own `POST /api/settings`, invisible to the settings-persistence
source extraction (which reads only `SettingsTab.tsx`'s own literal), and
already proven for the `position_estimation_*` key family. CLAUDE.md's
`SettingsDraft` recipe applies to settings `SettingsTab` itself renders; the
`VALID_SETTINGS_KEYS` + `GLOBAL_ONLY_SETTINGS_KEYS` half of that recipe still
applies in full and is mandatory. **Veto candidate.**

**P3-D5. Info-group volume is solved by collapse-plus-incremental-render, not
pagination.** The problem is that 553 info cards bury three warnings, which one
collapsed heading fixes; pagination adds controls and ordering guarantees for a
list users mostly skim. No server change, so no new endpoint contract. A
per-issue-type tally above the group makes the shape legible without expanding.
**Veto candidate** (the alternative is server-side pagination, which would also
need a stable sort key and a count endpoint).

**P3-D6. `TAK_TRACKER` joins TRACKER and SENSOR in C2's exempt set.** The epic
says "non-TRACKER/SENSOR"; a TAK tracker exists to report position frequently
and would fire on every correctly configured ATAK node.

**P3-D7. Dismiss/restore are gated on `settings:write` plus a per-caller
visibility check, not on `nodes:write`.** `mesh_issues` is global, dismissal is
global state, and every other `nodes:write` call site is source-scoped, so an
unscoped `nodes:write` here would be a novel use of that resource. `run-now` in
the same router already uses `settings:write`. The visibility check (intersect
the row's `sourceIds` with the caller's permitted set, 404 on empty) is what
stops a `settings:write` holder with narrow node read from dismissing or probing
a finding it cannot see. **Veto candidate.**

**P3-D8. C1 emits one `C1_key_security` finding per node with a `clauses` array,
not one finding per flag.** Three flags on one node would otherwise mean three
cards saying nearly the same thing, and they share one remedy.

**P3-D9. C1 adds no threshold of its own.** All three C1 conditions read flags
that `duplicateKeySchedulerService` already computes against its own thresholds
(`TIME_OFFSET_THRESHOLD_MINUTES`, default 30, is an env var). A second threshold
here could disagree with the flag and produce a finding the Security tab does
not show, or the reverse.

**P3-D10. B7 gets its own enable toggle; no other rule does.** B7 is the only
rule observed firing at pathological volume (553 findings on a real mesh), and
it is `info`/`low` by construction. Fourteen per-rule keys would be surface area
without evidence of need.

**P3-D11. `AUTO_CLOSE_CLEAN_RUNS` stays a code constant.** Considered for
exposure and rejected to keep the settings surface tight, but the docs page must
state the interaction: at the default 24 h cadence a resolved finding disappears
after about 3 days, and an operator who sets the cadence to 1 h gets 3 hours
instead. If users ask, this is the first knob to add.

**P3-D12. `counts.critical/warning/info` keep their Phase 1 meaning (over the
returned set) and `counts.dismissed` is added.** Redefining them to exclude
dismissed rows would change behaviour for the default request, which does not
return dismissed rows anyway, and would break existing tests for no gain.

## 11. Epic items weakened, deferred, or out of scope

### 11.1 C2's candidate gate is a mean, not a median

Covered in §2.5 and P3-D2. **What is lost:** a node whose broadcasts arrive in a
tight burst and then goes silent for days has an inflated mean and can fall
outside the candidate set, so its true fast median is never computed. That is an
under-flag, consistent with D3, D9 and the epic's general preference for
under-flagging when the recommendation is a configuration change. The docs page
states it.

### 11.2 A5's telemetry-cadence clause stays deferred

P1 §5.1 deferred it because the only durable solicited/unsolicited discriminator
is a join to `packet_log`, which is opt-in, off by default, per-source and
pruned. Phase 3 does **not** enable it. Phase 3 does add the machinery that
would make a future attempt cheaper (`coverage.evidence.packetLog` tells the
report whether the join is even possible), but firing a rule on a signal that is
absent on most installs is still a false-positive generator. The `rules.ts`
comment and the evidence field `telemetryCadenceClause: 'deferred'` stay as they
are. Recorded as a post-epic follow-up.

### 11.3 Notifications remain out of scope

Findings still emit no `dataEventEmitter` events (P1 §5.11). Routing them onto
the bus would fan them out to the automation engine, Apprise, desktop and
MQTT-publish subscribers, which is mesh-impact checklist §2 "indirect spam", and
whether mesh issues should notify at all is a user decision that was never taken.
**Post-epic follow-up issue:** "Mesh Issues notifications (opt-in, rate-limited,
severity-gated)", to be specced with the checklist and explicit user sign-off on
the cap.

### 11.4 Other follow-ups recorded, not done

- Server-side pagination of `GET /api/analysis/mesh-issues` if finding counts
  grow past a few thousand (§1.3).
- Exposing `AUTO_CLOSE_CLEAN_RUNS` (P3-D11).
- Extracting `resolvePermittedSourceIds` from `analysisRoutes.ts` so
  `meshIssuesRoutes.ts` can stop carrying a copy (P1 §5.13; still not worth
  touching a 1000-line module in a polish phase).
- MeshCore sources are still excluded from the analysis entirely
  (`meshcore_nodes` is a separate table with no `role`/`airUtilTx` equivalent).
  Unchanged from Phases 1 and 2, and out of scope for this epic.
